This lab is a demonstration of written program code's relationship with the CPU of our computers. Written code turns into smaller blocks of work that live in the CPU, which include [**machine instructions**](https://pages.cs.wisc.edu/~markhill/cs354/Fall2008/notes/basics.html), [**memory reads/writes**](https://pages.cs.wisc.edu/~markhill/cs354/Fall2008/notes/basics.html), [**cache behavior**](https://www.cs.cornell.edu/courses/cs3410/2024fa/notes/caches.html), and [**performance differences**](https://www.cs.cornell.edu/courses/cs3410/2025sp/notes/pipelining.html). We write and showcase all of this in the form of constructing basic matrix multiplication (matmul), since this computation is fundamental in Machine Learning workloads and hardware accelerator designs.

# CPU Execution Lab: Setup, Workflow, and Submission Guide

This guide takes you from a new computer setup to a complete individual pull request for Lab 1. Every student should implement the full lab in their own fork of the repository. Your pull request will contain your code, while the pull request description will serve as your lab report.

The instructor will review the individual implementations, results, and explanations and may combine the strongest ideas into the shared benchmark and final main program.

## 1. What This Lab Is About

This lab asks one central question:

> How much can performance change when the computation stays the same but the data moves differently?

You will investigate that question through:

- strided array access;
- row-first and column-first matrix traversal;
- memory-copy bandwidth;
- naive matrix multiplication;
- matrix multiplication using a transposed copy of B;
- serial and threaded array summation; and
- selected assembly generated by the compiler.

This is an introductory systems lab, but it also establishes ideas that will return later in the Blackhole project: data layout, local memory, explicit data movement, parallel workers, regular matrix computation, and the relationship between source code and machine execution.

## 13. Recommended Implementation Chronology

Everyone should attempt the full lab. The order below follows the concepts introduced by the source files and lets each experiment build on the previous one.

### Step 1: Read bench.h

Start with **include/bench.h**. It shows the public functions available across the program.

Do not change a function name, return type, or argument list merely to make an implementation easier. The header is a shared contract between main.c and the experiment files.

### Step 2: Read timer.c

The timer is prewritten infrastructure. Understand:

- why it uses a monotonic clock;
- why it returns a double measured in seconds;
- how main.c can calculate elapsed time as end minus start; and
- why allocation, initialization, and printing usually belong outside a timed region.

You should use benchmark_time_seconds() rather than adding unrelated timing methods to individual experiment files.

### Step 3: Read machine_info.c

The machine-information function is also prewritten infrastructure. Understand why benchmark results need context:

- operating environment;
- CPU architecture;
- compiler;
- compiler version; and
- logical CPU core count.

Call this function from main.c so the terminal output copied into your pull request identifies the machine used.

### Step 4: Implement stride_access.c

This is the first experiment implementation.

Your function should:

- read every array element exactly once;
- change the order of those reads according to the stride;
- return a checksum as a double;
- avoid allocation, timing, and printing; and
- handle the edge conditions described in the file.

Test several strides while keeping the amount of useful data and arithmetic comparable.

### Step 5: Implement row_col_access.c

Implement both matrix traversal functions:

- sum_matrix_by_rows();
- sum_matrix_by_columns().

Both should read the same flat row-major matrix and return the same mathematical sum, allowing for a possible small floating-point difference. Only the traversal order changes.

This is the clearest bridge between one-dimensional memory addresses and the way a two-dimensional matrix is visited.

### Step 6: Implement bandwidth_copy.c

Implement the element-by-element copy.

Keep the copying function focused on reads and writes. Validate the destination and calculate effective bandwidth in main.c, outside the timed function.

Use:

~~~text
useful bytes moved = 2 * length * sizeof(float)
effective GB/s = useful bytes moved / elapsed seconds / 1000000000.0
~~~

The factor of two represents one useful read from the source and one useful write to the destination.

### Before Matmul: Storage Layout and Floating-Point Throughput

**Storage order** describes how a matrix is arranged in a flat array. For a matrix with `rows` rows and `columns` columns:

- Row-major storage places each row together: `matrix[row * columns + column]`.
- Column-major storage places each column together: `matrix[column * rows + row]`.

**Traversal order** describes which element the loops visit next. The row and column traversal experiment uses row-major storage in both functions; visiting columns first does not change the storage layout.

For example, the matrix `[[1, 2, 3], [4, 5, 6]]` is stored as `[1, 2, 3, 4, 5, 6]` in row-major order and `[1, 4, 2, 5, 3, 6]` in column-major order. A row-major copy of the transpose has the same flat arrangement as a column-major copy of the original matrix. In Step 8, A stays row-major while the transposed buffer makes B's original columns contiguous. The result is still **A multiplied by B**.

A **FLOP** is one floating-point arithmetic operation, such as an addition or multiplication. A multiply followed by an add counts as two FLOPs, even if the processor uses one fused multiply-add instruction. FLOPs count work; **FLOP/s** measures how much work completes per second.

- **GFLOP/s** means billions (`10^9`) of floating-point operations per second.
- **TFLOP/s** means trillions (`10^12`) of floating-point operations per second.
- `1 TFLOP/s = 1000 GFLOP/s`. A TFLOP without `/s` is a trillion operations, not a rate.

Each of the `n * n` output elements in square matmul needs `n` multiplications and approximately `n` additions. Use the conventional approximate work count `2 * n * n * n`:

~~~text
GFLOP/s = (2.0 * n * n * n) / elapsed_seconds / 1e9
TFLOP/s = (2.0 * n * n * n) / elapsed_seconds / 1e12
~~~

Starting with `2.0` makes the calculation floating-point and avoids computing the entire operation count with integer multiplication first. Report both units in main.c; timer.c only supplies elapsed seconds and does not know how much arithmetic an experiment performs. Copy bandwidth remains GB/s because it measures useful data movement.

Both matmul implementations perform approximately the same arithmetic. If better memory locality halves execution time, achieved GFLOP/s and TFLOP/s double. For example, approximately two billion operations in 0.1 seconds gives 20 GFLOP/s, or 0.020 TFLOP/s; completing that same work in 0.05 seconds gives 40 GFLOP/s, or 0.040 TFLOP/s. The processor's theoretical peak has not changed. These are measured rates for this workload, and a speedup is not guaranteed for every matrix size or machine.

Compare kernel-only speedup (`naive_time / prepared_kernel_time`) and one-use speedup including preparation (`naive_time / (transpose_time + prepared_kernel_time)`). If you report end-to-end throughput, divide the matmul operation count by the combined transpose and multiplication time and label it explicitly. The transpose moves data; it does not add matmul arithmetic to the numerator.

### Step 7: Implement matmul_naive.c

Implement the direct three-loop definition of square matrix multiplication.

For each output C[i,j], accumulate:

~~~text
A[i,k] * B[k,j]
~~~

over k.

Keep allocation, initialization, timing, validation, and performance reporting in main.c.

An approximate operation count is:

~~~text
2 * n * n * n floating-point operations
~~~

From this, main.c can calculate approximate GFLOP/s and TFLOP/s.

### Step 8: Implement matmul_transposed.c

First implement the function that creates a separate transposed copy of B. Then implement the matmul that reads B's original columns as neighboring values in the transposed storage.

The result must still be A multiplied by B. It is not a different mathematical multiplication.

Measure the transpose cost separately from the multiplication so your report can distinguish:

- preparation cost;
- kernel time; and
- the possible benefit when the same prepared matrix is reused.

### Step 9: Implement threaded_sum.c

Implement:

- the serial baseline;
- the private pthread worker;
- the division of the array into non-overlapping ranges;
- thread creation;
- thread joining;
- partial-sum combination; and
- cleanup of thread-related allocations.

Every worker should write to its own partial sum. Do not have every thread repeatedly update one shared sum.

Compare the serial and threaded results for correctness before interpreting speedup:

~~~text
speedup = serial elapsed seconds / threaded elapsed seconds
~~~

Threading is not guaranteed to make a small workload faster. Thread creation, scheduling, joining, and result combination all have costs.

### Step 10: Complete main.c

Use the stages already placed in main.c as the integration checklist.

Main should eventually:

1. print machine information;
2. select array sizes, matrix sizes, strides, repetitions, and thread counts;
3. allocate and initialize inputs;
4. run each experiment;
5. measure elapsed time;
6. verify results;
7. calculate useful metrics;
8. print readable comparisons; and
9. free every successful allocation.

The experiment functions should remain focused. Main is where the complete benchmark is assembled.

### After Each Step

Do not wait until every file is finished before compiling.

A useful cycle is:

1. implement one focused function;
2. remove only the temporary unused-parameter lines replaced by your implementation;
3. compile with all warnings enabled;
4. fix errors and warnings;

## 14. Benchmarking Expectations

A benchmark is more than code that prints a time.

### Verify Correctness First

A faster incorrect implementation is not a successful result.

Use checksums or output comparisons so that:

- stride variants read all expected elements;
- row and column traversals agree;
- the copy destination matches the source;
- both matmul versions produce matching output matrices; and
- serial and threaded sums agree within a reasonable floating-point tolerance.

### Keep Setup Work Outside the Timed Region

Unless you are intentionally measuring setup cost, do not include these inside a kernel timing:

- memory allocation;
- input initialization;
- result printing;
- correctness checking; or
- unrelated file operations.

Transpose time is important, but report it separately from the transposed matmul kernel.

### Run More Than Once

One run can be affected by other programs, scheduling, temperature, power settings, and cache state. Test each important case more than once and state how you summarized repeated measurements.

Possible summaries include:

- minimum time;
- median time; or
- arithmetic mean.

Whichever method you choose, document it in the pull request.

### Compare Fairly

When comparing two versions:

- use the same inputs;
- use the same compiler command;
- use the same optimization level;
- test on the same machine;
- perform equivalent correctness checks; and
- keep the amount of mathematical work comparable.

### Interpret Before Comparing Computers

First compare patterns on your own machine. Absolute times from two students may differ because their processors, memory systems, compilers, operating environments, and background workloads differ.

The main result is the relationship between variants, not a contest for the smallest number.
