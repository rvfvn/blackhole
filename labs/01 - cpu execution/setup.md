# CPU Execution Lab 
### September 14th - 18th, 2026

This lab is a demonstration of written program code's relationship with the CPU of our computers. Written code turns into smaller blocks of work that live in the CPU, which include [**machine instructions**](https://pages.cs.wisc.edu/~markhill/cs354/Fall2008/notes/basics.html), [**memory reads/writes**](https://pages.cs.wisc.edu/~markhill/cs354/Fall2008/notes/basics.html), [**cache behavior**](https://www.cs.cornell.edu/courses/cs3410/2024fa/notes/caches.html), and [**performance differences**](https://www.cs.cornell.edu/courses/cs3410/2025sp/notes/pipelining.html). We write and showcase all of this in the form of constructing basic matrix multiplication (matmul), since this computation is fundamental in Machine Learning workloads and hardware accelerator designs. 

Matmuls also work quite well for showing how data moves differently based on simple changes within the operation itself. Tenstorrent's Blackhole, then, can be thought of as a later extension of these same ideas, but at scale, with topics that this lab should serve as a foundation for: 
- [**local memory near compute**](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/labs/matmul/lab1/lab1.html), 
- [**many parallel workers**](https://docs.tenstorrent.com/aibs/blackhole/installation.html), 
- [**explicit data movement**](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/apis/kernel_apis/data_movement/data_movement.html), 

and 

- [**specialized hardware for ML-shaped computation**](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/advanced_topics/compute_engines_and_dataflow_within_tensix.html).

# CPU Execution Lab: Setup, Workflow, and Submission Guide

This guide takes you from a new computer setup to a complete individual pull request for Lab 1. Every student should implement the full lab in their own fork of the repository. Your pull request will contain your code, while the pull request description will serve as your lab report.

The instructor will review the individual implementations, results, and explanations and may combine the strongest ideas into the shared benchmark and final main program.

## 1. What This Lab Is About

This lab asks one central question:

> How much can performance change when the computation stays the same but the data moves differently?

You will investigate that question through:

- row-first and column-first matrix traversal to explore stride and cache locality;
- naive matrix multiplication;
- matrix multiplication using a transposed copy of B; and
- selected assembly generated by the compiler.

This is an introductory systems lab, but it also establishes ideas that will return later in the Blackhole project: data layout, local memory, explicit data movement, parallel workers, regular matrix computation, and the relationship between source code and machine execution.

Start here:

~~~sh

~~~

`build.sh` is a shell script: a file containing terminal commands. It compiles the selected experiment (for example, `lab2.c`) together with `lib/bench.c`, links them into `a.out` in the lab folder, then runs it. Other lab source files are not needed. If compilation fails, the script stops before running anything.

| Command | Experiment | Experiment function |
| --- | --- | --- |
| `./build.sh 1` | Row/column access, stride, and caches | `main()` in lab1.c |
| `./build.sh 2` | Naive matmul and FLOP/s | `main()` in lab2.c |

Run `./build.sh` to see the menu or `./build.sh all` to compile and run all three in sequence. Each build replaces a.out; after `all`, a.out contains lab 3. Running `./a.out` directly repeats the most recently built lab. You can also use `sh build.sh 1` if your checkout does not mark the script executable. The script works when invoked from another directory too.

The compilation command is maintained in build.sh. Its flags select C11, enable normal optimization (`-O2`), show warnings, and set the lab directory as an include search path (`-I.`). `-fno-inline` keeps the computation functions as calls so the compiler does not inline repeated benchmark work into the driver. Do not change compiler options between comparisons.

## 12. C File Organization: Declarations, Definitions, and Linking

A **function** is a named piece of work. A **call** asks it to perform that work. A **declaration** tells the compiler the function's name, inputs, and return type. A **definition** provides the instructions in braces.

We use a common C convention: put a shared function's declaration in a `.h` header and its definition in a `.c` source file. For example, `lib/bench.h` declares:

~~~c
double elapsed_since(double start);
~~~

This says the function takes a `double` named start and returns a `double`. The semicolon ends the declaration; it does not run the function. `lib/bench.c` defines its behavior:

~~~c
double elapsed_since(double start) {
    double elapsed = benchmark_time_seconds() - start;
    require(elapsed > 0.0, "timer interval must be positive");
    return elapsed;
}
~~~

A lab includes the declaration and calls the function:

~~~c
#include "lib/bench.h"

/* Inside the experiment, after recording start and doing the work: */
double elapsed = elapsed_since(start);
~~~

Including the header lets the compiler check the call. It does not supply the implementation. The build compiles the selected lab and the helper source, then **links** them so the call reaches the definition. For example, build.sh runs:

~~~sh
cc -std=c11 -O2 -fno-inline -Wall -Wextra -pedantic -I. lab2.c lib/bench.c -o a.out
~~~

The `#ifndef`, `#define`, and `#endif` in bench.h form an **include guard**, preventing the header from being processed twice in one compilation unit. Headers such as `<stdio.h>` come from the C implementation; lib/bench.h is our shared project header. Include the header, not the `.c` file.

Functions used only inside one lab are marked `static`. Each lab defines its computation functions before main, so the compiler has seen them before they are called. Here, `static` means the function belongs to that source file rather than being a shared library interface.

`int main(void)` means main takes no arguments and returns an integer exit status. Execution starts in main, which contains the supplied benchmark and calls the computation functions above it. `size_t` is an unsigned integer type used for sizes, and `const float *matrix` lets a function read the input values without modifying them through that pointer.

Start by editing the lab's computation loops. Treat the helpers in lib/ as supplied infrastructure until you need to understand their internals. Keep shared declarations in bench.h, shared implementations in bench.c, and experiment-specific code in the corresponding lab file.
